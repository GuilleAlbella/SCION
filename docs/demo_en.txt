CHOSEN OBJECT AND WHY
--------------------------------------------------------------------------------
The whole demo revolves around ONE table: core_banking.transactions.

Why this one:
  * It is the MOST-QUERIED table in the warehouse (31,200 queries, 42 users).
    -> Any change here is expensive.
  * It has changes across 4 different snapshots (4, 5, 6 and 9).
    -> Timeline and Changes are rich.
  * It covers 4 distinct change types (TYPE_CHANGED, NULLABILITY,
    POSITION, REMOVED) -- the ONLY object that triggers
    COLUMN_POSITION_CHANGED in the whole seed.
  * It uses exotic Teradata types: ST_GEOMETRY, CLOB, TIMESTAMP WITH TIME
    ZONE, INTERVAL DAY TO SECOND, DECIMAL widening, CHAR(3) currency.
  * It sits at the centre of the network: 2 upstream, 3 downstream
    (including a stored procedure and a trigger). The graph shines.
  * Classified as HIGH in Criticality.
  * Shows up in the statistical anomaly alerts for snapshot #10.

THE STORY OF THE TABLE (tell this as you advance through the demo)
  S1 (baseline) -- the table is born with 12 columns, including a BLOB
                   (raw_payload) that stores the original request of
                   every transaction.
  S4 -- a new capital-adequacy regulation requires widening `amount`
        from DECIMAL(18,2) to DECIMAL(22,2). A BREAKING type change.
  S5 -- data quality detects transactions arriving without an amount
        (adjustments, reversals...). `amount` is loosened to NULLABLE.
  S6 -- performance optimisation: columns are reordered so `currency`
        sits next to `amount` and `channel`/`description` move back.
  S9 -- GDPR audit forces DROPPING `raw_payload` (it contained PII
        in an opaque format that could not be anonymised). BREAKING,
        HIGH severity.
  S10 -- current state.

The storytelling is "realistic lifecycle of a core table" with 4
typical drivers of change (regulation, data quality, performance,
compliance). Any DBA or EDW architect recognises the pattern.

  b) Section 2 -- Detailed changes (Table mode by default)

        counter next to it: "Match: 5 of 31".

                    core_banking.transactions.amount

================================================================================
 FALLBACKS AND TROUBLESHOOTING
================================================================================

If something does not appear or looks odd during the demo:

  [X] Empty graph on /lineage
    -> Check the selected snapshot has nodes (snapshot #10).
    -> Check the amber warning "object not in this snapshot".
    -> If you came from a column change, check the green banner
       explaining the redirect to the parent table.

  [X] No criticality computed
    -> Re-run tools/rich_seed.py. Takes ~30 seconds.

  [X] DDL generator says "no changes selected"
    -> Tick at least one row with the checkbox before clicking
       Generate DDL.

  [X] TAISA says "LLM provider not ready"
    -> Check GROQ_API_KEY is set in backend/app/config/taisa_llm.yaml.
    -> Fallback is the mock_llm_provider which answers with a generic
       text.

  [X] "Blast radius" vs "Impact spread"
    -> In v1.09.00 we renamed "Blast radius" -> "Impact spread" across
       the user-facing UI. Backend API field names (result.blast_radius)
       are unchanged -- it is a UI-only rename.

  [X] Intelligence shows "Structural Stability: Unknown"
    -> Check the snapshot has compute_snapshot_metrics run (should be
       automatic with rich_seed, but if it was interrupted it may be
       missing).

  [X] Impact detail shows 0 direct / 0 indirect
    -> Fixed in v1.10.03: column-level changes now resolve to the
       parent table for impact tracing. If you still see zeros, re-run
       rich_seed.py once.

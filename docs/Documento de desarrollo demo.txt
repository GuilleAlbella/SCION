🔹 PUNTO 2 – Definición de Metadata Query Templates (motor-agnostic)
🎯 Objetivo

Definir un catálogo único y canónico de templates de metadata, independiente del motor de base de datos, que permita:

Extraer metadata estructural de cualquier EDW

Evitar lógica duplicada por motor

Garantizar consistencia semántica

Simplificar mantenimiento y escalabilidad

Este punto reemplaza el concepto de “conectores inteligentes” por un modelo basado en templates + adaptadores.

2.1 Principios de diseño de los templates

Los templates deben cumplir:

Ser agnósticos al motor

Describir qué se quiere obtener, no cómo

Tener salida estructurada conocida

No contener SQL nativo

Ser reutilizables por cualquier adaptador

2.2 Ubicación de los templates

Crear el directorio:

backend/app/connectors/templates/


Todos los templates se definen en formato YAML.

2.3 Estructura estándar de un template

Cada template debe seguir esta estructura mínima:

template_name: list_tables
description: Returns all tables and views for a given schema
inputs:
  - name: database
    required: true
  - name: schema
    required: true
output:
  columns:
    - name: database_name
      type: string
    - name: schema_name
      type: string
    - name: table_name
      type: string
    - name: object_type
      type: string

2.4 Templates mínimos obligatorios (MVP)

Campos de salida:

2.4.3 list_tables.yaml

Campos de salida:

2.5 Convenciones de nombres y tipos

object_type: TABLE | VIEW | PROCEDURE

Tipos de datos normalizados

Nombres técnicos, no de negocio

2.6 Validación de templates

Crear validación automática que verifique:

🔹 PUNTO 3 – Implementación de Adaptadores por Motor (Template → SQL)
🎯 Objetivo

Implementar un sistema de adaptadores livianos por motor de base de datos, responsables de:

Traducir templates canónicos de metadata a SQL nativo

Desacoplar completamente la lógica del motor del core del sistema

3.1 Principios de diseño de los adaptadores

Cada adaptador debe:

Implementar una interfaz común

Conocer solo su motor

No contener lógica de negocio

No persistir datos

No conocer el modelo interno

🔹 PUNTO 4 – Snapshot Engine y persistencia de metadata
🎯 Objetivo

Implementar el Snapshot Engine, responsable de:

Ejecutar templates de metadata vía adaptadores

No realizar lógica de diff ni análisis

6.5 Impact Analysis (consultas recursivas)

Definir consultas estándar para:

Impacto directo

Impacto indirecto

Profundidad configurable

Ejemplo conceptual:

WITH RECURSIVE impact AS (
  SELECT target_node_id
  FROM graph_edge
  WHERE source_node_id = :changed_node
  UNION ALL
  SELECT ge.target_node_id
  FROM graph_edge ge
  JOIN impact i ON ge.source_node_id = i.target_node_id
)
SELECT * FROM impact;
